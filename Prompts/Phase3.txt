============================================================
PHASE 3 — NLP TEXT PREPROCESSING
============================================================

PROJECT:
Sarcasm & Irony Detection System using NLP

PROJECT TYPE:
MCA Final-Year NLP + Machine Learning Project

ROLE:
Act as a senior NLP engineer, machine-learning engineer, and
research-oriented NLP mentor.

Your responsibility in this phase is to design and implement the
complete NLP text-preprocessing layer for the four-class sarcasm
and irony classification project.

============================================================
1. PHASE OBJECTIVE
============================================================

Phase 3 converts the validated dataset from Phase 1 and the
findings from Phase 2 into reusable NLP preprocessing pipelines.

The goal is NOT to create one blindly cleaned dataset.

Instead, investigate and implement preprocessing strategies that
preserve information potentially useful for sarcasm and irony.

The main pipeline is:

RAW/CLEAN TEXT
      ↓
TEXT NORMALIZATION
      ↓
SOCIAL-MEDIA NORMALIZATION
      ↓
TOKENIZATION
      ↓
OPTIONAL STOPWORD HANDLING
      ↓
OPTIONAL LEMMATIZATION
      ↓
OPTIONAL STEMMING
      ↓
N-GRAM READY TEXT
      ↓
MODEL-SPECIFIC REPRESENTATION

The output of this phase will be used by later phases for:

- Bag of Words
- TF-IDF
- N-grams
- Classical ML
- Linguistic feature engineering
- Bi-LSTM
- BERT

============================================================
2. IMPORTANT PROJECT RULE
============================================================

Do NOT assume that aggressive preprocessing improves sarcasm
detection.

For example, do NOT automatically:

- remove punctuation
- remove emojis
- remove hashtags
- remove capitalization
- remove repeated characters
- remove negations
- remove all stopwords
- stem everything
- lemmatize everything

These can carry useful sarcastic/ironic signals.

Instead, create controlled preprocessing variants and compare them
later during model experiments.

============================================================
5. IMPORTANT DATA LEAKAGE RULE
============================================================

Any preprocessing component that LEARNS information from text must
be fitted only on training data.

Examples:

- vocabulary
- TF-IDF vocabulary
- tokenizer vocabulary
- frequency-based feature selection
- embedding vocabulary where learned from project data

Correct:

TRAIN
 ↓
FIT preprocessing
 ↓
Transform validation
 ↓
Transform test

Never:

TRAIN + TEST
 ↓
FIT preprocessing

The official test set must remain unseen for model development.

============================================================
7. TEXT VALIDATION
============================================================

Create a function such as:

validate_text(text)

It must safely handle:

- None
- NaN
- empty strings
- whitespace-only strings
- non-string input

Return a safe normalized representation.

Since Phase 1 should already have removed invalid records,
unexpected invalid input should be logged rather than silently
ignored.

============================================================
8. WHITESPACE NORMALIZATION
============================================================

Normalize:

- repeated spaces
- tabs
- unnecessary line breaks

Example:

"this    is   great"

→

"this is great"

Do not remove meaningful punctuation or social-media signals.

============================================================
9. URL NORMALIZATION
============================================================

URLs should generally be normalized rather than simply deleted.

Example:

"https://example.com/page"

→

"URL"

or an equivalent consistent placeholder.

The exact placeholder must be consistent throughout the project.

Recommended:

URL

Reason:

A URL may carry little lexical information for sarcasm classification,
but the presence of a URL can still be useful as a structural signal.

Also preserve a binary/count feature for later feature engineering:

has_url
url_count

Do not discard the information completely.

============================================================
10. USER MENTION NORMALIZATION
============================================================

Normalize:

@username

to:

USER_MENTION

Do not retain individual usernames as vocabulary features.

Reason:

Usernames are usually not useful for generalization.

Also preserve:

has_mention
mention_count

for later feature engineering.

============================================================
11. HASHTAG HANDLING
============================================================

Do NOT simply remove hashtags.

Investigate two representations.

Representation A:

Keep hashtag as a token.

Example:

#sarcasm

→

#sarcasm

Representation B:

Separate hashtag marker from its lexical content where possible.

Example:

#sarcasm

→

sarcasm

For compound hashtags:

#WhatAGreatIdea

attempt reasonable segmentation only if reliable.

Do not use an unreliable word-segmentation algorithm that damages
the text.

Preserve:

hashtag_count

for later feature engineering.

The final strategy should be selected based on experiments in later
phases.

============================================================
12. EMOJI HANDLING
============================================================

Do NOT remove emojis blindly.

Sarcasm frequently uses:

- 😂
- 🙃
- 😒
- 😐
- etc.

Create an option to:

A. Preserve emojis.

B. Convert emojis to textual descriptions if appropriate.

Do not force emoji-to-text conversion for all models.

The primary classical pipeline should preserve emoji information
where technically practical.

Also calculate:

emoji_count
has_emoji

for later feature engineering.

============================================================
13. PUNCTUATION HANDLING
============================================================

Do NOT automatically remove punctuation.

Important patterns may include:

!!!
???
!?
...
""
'"

Examples:

"Great!!!"

"Really???"

"Oh... wonderful."

Punctuation can convey tone.

Create preprocessing variants:

Variant A:
Punctuation preserved.

Variant B:
Limited punctuation normalization.

Do not create a default variant that deletes all punctuation
without experimental justification.

============================================================
14. CAPITALIZATION
============================================================

Do not blindly lowercase the original dataset.

Create two possible representations:

A. Case-preserving text.

B. Lowercase text.

Reason:

Capitalization can indicate emphasis.

Example:

"WHAT A GREAT IDEA"

may carry a different tone from:

"what a great idea"

The classical baseline can later compare both approaches.

============================================================
15. REPEATED CHARACTER HANDLING
============================================================

Social-media text may contain:

soooo
goooood
loooool
greatttt

Do not automatically reduce all repeated characters.

Create an optional normalization function.

Example:

"sooooo good"

could become:

"soo good"

or another controlled representation.

However, the original repeated-character information should remain
available for feature engineering.

Preserve:

repeated_character_count

where practical.

============================================================
16. NEGATION HANDLING
============================================================

Do NOT remove negation words blindly.

Important negations include:

not
no
never
n't
nothing
nobody

For sentiment-like and sarcasm-related classification,
negation can be important.

Create preprocessing logic that preserves negation.

If stopword removal is tested later, make sure negation words are
protected.

============================================================
17. TOKENIZATION
============================================================

Implement tokenization appropriate for social-media text.

Use an NLP library such as:

NLTK

or another approved library if technically better.

The tokenizer should handle:

- words
- punctuation
- hashtags
- mentions
- URLs
- contractions
- emojis where supported

Do not use a simplistic split(" ") as the final NLP tokenizer.

Whitespace splitting may be used only for simple EDA statistics.

============================================================
18. STOPWORD HANDLING
============================================================

Do NOT permanently remove stopwords.

Create two preprocessing configurations:

CONFIG A:
Stopwords retained.

CONFIG B:
Stopwords removed.

IMPORTANT:

Protect negation words.

For example:

not
never
no

should not disappear simply because they appear in a stopword list.

The effect of stopword removal will be tested later using actual
classification experiments.

============================================================
19. LEMMATIZATION
============================================================

Implement optional lemmatization.

Example:

running
runs
ran

may be mapped toward:

run

Use an appropriate NLP library.

Do not make lemmatization mandatory for all model pipelines.

Create:

lemmatization_enabled = True/False

The effect will be evaluated later.

============================================================
20. STEMMING
============================================================

Implement optional stemming for experimental comparison.

Possible tool:

NLTK PorterStemmer

However:

Do not automatically use stemming in the final pipeline.

Reason:

Stemming can damage informal social-media words and may remove
useful semantic information.

Stemming is an experiment, not a default.

============================================================

============================================================

Maintain separate variants:

Later experiments will determine which representation performs best.

Do not claim that lemmatization is automatically superior.

50. IMPORTANT NLP PRINCIPLE
============================================================

Sarcasm and irony are difficult because the literal words may not
represent the intended meaning.

Therefore, preprocessing must preserve potentially useful signals:

- punctuation
- capitalization
- emojis
- hashtags
- repeated characters
- negations
- informal language

Do not treat these as noise automatically.

The project should scientifically determine their usefulness through
later experiments.
